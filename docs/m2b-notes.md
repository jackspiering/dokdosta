## Decisions the plan leaves open

1. **Fixed paths.** Host plugin mounted read-only at `/host/docker-compose`; bundled copy at `/usr/libexec/whalenurse/docker-compose`. They are different paths on purpose: "bundled" (and with it the version-skew check) comes from the path that matched, never from comparing versions. Under systemd, the host's plugin directories (`/usr/libexec/docker/cli-plugins/…` and three more) are searched last. An explicit `WHALENURSE_COMPOSE_BIN` that does not work is an error, never a reason to use another binary.
2. **The image comparator goes through the API, not a shell-out.** The image has no `docker` CLI. `docker.Reader.ImageID` is `ImageInspect` with `ImageInspectWithPlatform(linux/<arch>)` and returns `.ID`: the call behind `docker image inspect --platform linux/<arch> --format '{{.Id}}'`. The arch is the Engine's (`ServerVersion().Arch`). The integration tests pin it on both stores and on three compose releases (see *Tests*).
2a. **Found by the CI matrix: the compose image label differs by release (needs approval, plan v3.6 item 3).** On the containerd store, compose v5.2.0 writes the image (index) ID into `com.docker.compose.image`, where v5.6.0 writes the platform manifest digest (M0, M0b). The 5.2.0 × containerd leg blocked every recreate as "the tag moved" with `busybox:1.37 now resolves to 66a6306db78b, but this container was created from bdf57e528e45`; the classic store and 5.6.0/latest were unaffected, and the oracle, `config --hash`, the dependents recreate and the containerized recreate all behaved on 5.2.0. The guard now accepts a label equal to either the platform ID or the plain ID; a re-tag changes both. It is its own commit ("accept the index ID in the compose image label") if you would rather revert it. The cutover release was not pinned (somewhere in v5.3.0 to v5.5.0; plan v3.3 says v5.5.0 changed digest reconciliation).
3. **The oracle's output is read from stdout and stderr together.** Compose prints progress on stderr; M0 captured both merged. "Parsed, but no line about this container" and "no JSON at all" (an old compose prints `null`) are both `ErrUnparseable`, which means *fall back to `config --hash`*, never *no drift*. Lines are matched on the container's name (`Container <name>`, also the temporary `<id>_<name>` compose renames to).
4. **A failed oracle is a fallback, not a block.** If the dry-run command itself fails (not just unparseable), the guard reports it and tries `config --hash`; if that fails too, the finding is `unverified` and blocks like drift.
5. **Where the explicit image comparison runs.** Always for reference holders; after the hash fallback (the hash covers config only); and, to say *why*, when the oracle found drift (its failure is then ignored: the oracle's finding stands). A reference holder without a `com.docker.compose.image` label cannot be verified, which is a block in strict mode.
6. **Dependents are incidents of their own, not an ad hoc step.** A dependent whose parent ID is gone (`ClassStaleParentGone`, also a failed start with `No such container`) gets `ActionRecreateStale`; one whose parent restarted later gets `ActionRestart` (class `ClassStaleParentRestarted`). They go through the engine like anything else, so the flap limit, rate limit, cooldown, SUSPENDED and persistence apply. A dependent repaired by the dependents step does not count toward its own flap limit (maintainer decision, plan v3.6 item 10), so a flaky parent cannot SUSPEND its sidecar for flapping. After whalenurse's own action on a key, its dependents are scheduled for when the key is looked at again, and a parent that is back in a good state with an incident still open triggers the same sweep. The parent's own `start`/`create` events fall inside its in-flight window and are not interpreted (plan §3.2), which is why that explicit trigger is needed.
7. **Checks 2 and 3 of the guard run on dependents before the dependents `up`** (check 1 is skipped for them, plan §3.6). A non-forced `up` deploys on-disk changes if compose decides to recreate, so a re-tagged image or a bundled-compose skew blocks it. The on-disk compose file is *not* checked for a dependent (compose hashes it after resolving the reference; E4 and E5): the parent's own check, and the maintainer's habit of editing a file and running `up`, are what cover it.
8. **A stale dependent waits for the services it depends on** (from the `com.docker.compose.depends_on` label, which includes `network_mode: service:X`): all of them that have a container in the project must run and not be busy. Its old parent ID is gone, so the rules cannot see the new parent; the label is how the daemon finds it. No label means no wait; the post-check and the next look decide. The wait is not a refused action: it is one `WaitingForParent` event per reason (not an `ActionRefused` every GRACE), no rung or rate slot is spent, and the dependent is looked at again with the next poll (every 2 s while the service is being healed).
9. **One at a time, with a health wait, as scheduled steps.** `depGate` records, per parent reference, the dependent that was just restarted or recreated; its siblings are rescheduled every 2 s until it runs (and is healthy if it has a healthcheck) or 90 s have passed. No sleep, so the loop, the heartbeat and `/healthz` keep running and the unit tests run on the fake clock.
10. **Rate-limit slots.** Every `Begin` spends one slot of `WHALENURSE_RATE_LIMIT`: restart, recreate, and each dependent's restart or recreate. A blocked recreate (no `Begin`) spends none. With the default of 10 an hour, a parent recreate with two sidecars costs 3.
11. **Dependents of an opted-in parent are repaired without an opt-in of their own** (maintainer decision, plan v3.6 item 9), unless `whalenurse.enable=false`; only the dependents step, never their own ladder. Implemented in `rules.Classify` (`Input.DependentOfOptedIn`, `Decision.IsDependentStep`) and `Daemon.parentOptedIn`.
12. **Without compose, a recreate-shaped decision is advice.** If the gate is off, the container is not a compose container, its compose inputs are unreadable, or `whalenurse.actions` lacks `recreate`, `ActionRecreate`/`ActionRecreateStale` become `ActionNeedsRecreate`: one `NeedsRecreate` event, no incident, exactly what M2a did. The ladder of an ordinary unhealthy container instead records `RungUnavailable` for rung 2 and ends at SUSPENDED after rung 1, as the plan says.
13. **A network that is gone** (`network … not found`) is `ActionRecreate`: rung 2 straight away, restart skipped, drift guard first. Not reproduced (as in M0).
14. **Dry-run runs the guard.** It only reads (compose's own `--dry-run`, `config --hash`, an image inspect), so a dry run tells you "this recreate would be blocked: …". The mutating commands go to no-op actors (`docker.DryRun`, `compose.DryRun`).
15. **The compose child environment** drops `COMPOSE_*`, `DOCKER_CONTEXT`, `DOCKER_CONFIG` and `WHALENURSE_*` and sets `NO_COLOR=1`; the working directory is `/`. Variables that compose interpolates from the shell in the original `up` and that are not in an env file will resolve differently, which shows as config drift and blocks (the safe direction).
16. **`compose` exposes typed methods only** (`Recreate`, `Up`, `DryRunUp`, `ConfigHash`): `down` cannot be expressed. The integration guard re-checks every command line (`CheckComposeCommand`), so the tests fail closed even if the package grew a bug.
17. **Staleness through `ipc`/`pid`** is found by inspect (the poll inspects every opted-in container), but the container list carries only `NetworkMode`. The daemon therefore keeps the `container:` references of the last inspect per container ID (`Daemon.refs`) and inspects each new ID of a compose service without an opt-in once (`learnRefs`), so the poll and the sweep after a parent's `start` also schedule a sidecar without an opt-in that holds an `ipc:` or `pid:` reference. A container with no reference and no opt-in is not inspected again.

## What M2b built

- `internal/compose`: version parsing and the gate, `Project` from labels with a readability check that names the identical-path mount, the `Runner`, binary lookup, `Reader`/`Actor`/`DryRun`, the oracle and `config --hash` parsers, the drift `Guard`, a `Fake`.
- `internal/docker`: `ServerVersion`, `ImageID`, `Container.Image` and `VolumesFrom`.
- `internal/rules`: `ActionRecreate`, `ActionRecreateStale`, `ActionNeedsRecreate` (advice only), the stale-parent-restarted decision as an `ActionRestart` that waits for a busy parent.
- `internal/engine`: rung 2 in the ladder, `Obs.Unavailable`, `Blocked`, `Warned`, `Note`, `ReasonDrift`, new events (`DriftBlocked`, `DriftWarned`, `RungsDisabled`, `DependentPostCheck`).
- `internal/daemon`: the startup gate (re-checked after every stream reconnect), `executeRecreate`, the guard wiring, the stale-parent check, the dependents sweep and the sibling gate, the single notification for a parent left down, `status` fields.
- Image: the compose plugin bundled with a checksum; `examples/compose.yaml`, `README.md` and `docs/running.md` warn about the two mounts.
- CI: `scripts/ci/setup-docker.sh <store> [compose]` installs the release asked for with its checksum; the integration job is the 2 × 3 matrix.
- `test/m0/m0b/whalenurse-recreate/`: the throwaway-VM scenario.

## What CI covered, and what it did not

CI run [39084503271](https://github.com/jackspiering/whalenurse/actions/runs/39084503271) (the last on the PR): the 2 stores × 3 compose releases (v5.2.0, v5.6.0, latest = v5.6.0 today) integration matrix, the build/unit job, the shellcheck and self-test job and both `image-drift` jobs are green. Each integration leg runs rung 2 for real through the guarded compose runner, in `whalenurse-test-*` projects only:

- restart → recreate → SUSPENDED; a recreate that repairs what a restart cannot (a file in the writable layer); heal never pulls (a local-only tag with `pull_policy: always`, no image `pull` event, recreate succeeded); the guard blocks after a compose edit (oracle, and `config --hash` fallback) and after a re-tag (oracle, and the explicit comparison after the fallback), and does not block an unchanged container; a `network_mode` sidecar recreated after its parent's recreate by whalenurse and after an external one (non-forced `up`, never an API restart or start), restarted after its parent's restart, and blocked when its image tag moved (the explicit comparison on a reference holder, no oracle or hash run for it); the version gate with a faked old Engine; dry-run runs the read-only guard and no `up` that is not a dry run.
- A containerized whalenurse (read-only rootfs, uid 65532, the socket's group) recreates with the host plugin mounted read-only and the stacks directory mounted read-only at the identical path; compose needed no writable `HOME` or `/tmp`. With no host plugin it uses the bundled copy; when the host compose is another release (v5.2.0 legs) the container is not recreated and the finding is exactly "can't verify drift (compose 5.2.0 on host vs 5.6.0 in whalenurse)", neither a config nor an image finding. On the v5.6.0 legs it recreates.
- Evidence for plan v3.6 item 3 (the index ID in the label): in the first run the 5.2.0 × containerd leg failed five tests with the false "tag moved" finding while 5.2.0 × classic and every 5.6.0/latest leg passed; after the fix, that leg passes everything, including both re-tag subtests of `TestImageDriftGuardBlocksAfterAReTag` and `TestStaleDependentWithAMovedTagIsBlocked`, which prove the re-tag is still caught.

The `whalenurse-recreate` scenario on the VM (18 Oct 2026, Engine 29.9.1 containerd store, compose 5.6.0 from the host plugin, whalenurse in a container): `collect.sh --watch 240` RESULT: PASS, 0 WARN. The parent got `restart,recreate`, the sidecar only `recreate-stale` (non-forced `up`, no post-check needed), its network_mode points at the new parent, the namespaces are shared, the sidecar reaches the parent's httpd on its own loopback, nothing was blocked or SUSPENDED, and the containers outside the project are unchanged.

Not covered: anything beyond busybox (a real app, a compose file using `extends`/`include` from outside the stacks root, several projects sharing one tag), the hash fallback on a compose that prints `null` (parser unit tests only), Engine below 28.1 (faked), `ipc`/`pid` dependents (rules unit tests only), and the throwaway-VM scenario, which was prepared on this host (the maintainer confirmed it is a coding and testing VM) but whose step has not been run: see the report.

## Open questions: all answered (18 Oct 2026, plan v3.6)

1. Sidecars not opted in follow an opted-in parent unless labelled `whalenurse.enable=false` (items 9, decision 11).
2. Dependents repaired by the dependents step do not count toward their own flap limit (item 10).
3. `warn` overrides verified drift only; "can't verify" blocks (item 11).
4. Version skew of the host plugin is information in the drift message, not a block (item 12).
5. The index ID in the image label is accepted (item 3, approved).
