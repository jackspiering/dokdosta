## Decisions the plan leaves open

1. **`--policy always`** (plan v3.8 item 1; a deviation from the literal "compose pull <svc>"). The alternative, a bare `pull`, fails in the way the upstream check shows. The first build let the label override a deliberate `pull_policy: never` too; **the maintainer decided otherwise** (follow-up 4): `never` and `build` are respected.
2. **What "changed" means.** The platform image ID of the reference (`image inspect --platform linux/<arch>`, the drift guard's comparator), read before and after: it is what will run. An index that gained another platform is not a change. The rollback uses the **plain** ID read before the pull (the index digest on the containerd store), because a platform manifest digest may not be taggable. The integration test runs the rollback as pasted, on both stores.
3. **The guard before the pull.** Checks 1 and 3 only, as the task says. Compose's oracle says `Recreate` for a moved tag too, so a `Recreate` before a pull is a config finding unless `config --hash` still matches the label and the explicit comparison shows the image moved. (Since follow-up 1 there is no `restart,pull` ladder; the mode is also what rung 2 and the sidecar use, follow-ups 2 and 3.) In the normal ladder (restart, recreate, pull) the guard is nearly a no-op, because rung 2 has just recreated the container and rung 2's own guard SUSPENDS on a moved tag (v3.6 item 6), so a pull-labelled container whose tag was moved by a stack beside it is SUSPENDED at rung 2 with a drift block, not pulled. That is the approved v3.6 behaviour; see open question 2.
4. **Unchanged digest: immediate SUSPENDED.** `Result.Exhausted` ends the ladder without a cooldown, because nothing about the container changed. The giving-up message carries the cause; the pull's own `ActionResult` (outcome `unchanged`) is not notified, to keep it one message.
5. **Changed digest: the move is recorded before the `up`.** The tag moved for every stack that shares it whether or not the `up` works. `TagMoved` is emitted after the `up`, so the message can say whether the recreate worked; if it failed, the title says "pulled a newer image, but the recreate failed" and the rollback is still given. "Upgraded" is only said for a container that was really replaced: after the non-forced `up` the container ID must have changed and the container must run, otherwise it is recreated with `--force-recreate` (`UpgradePostCheck`), exactly as the dependents step does.
6. **Where the record lives.** The store's meta key `tagmoved:<normalized ref>` (JSON), not a new table: no schema migration, one row per reference, overwritten when the tag moves again, and never pruned (one small row per reference). A dry run stores nothing (it never pulls). The reference is normalized (`nginx`, `nginx:latest`, `docker.io/library/nginx:latest`), and a move is claimed only while the reference still resolves to what that pull produced.
7. **The upgrade message's size.** The rollback is two lines, `docker image tag <64-hex id> <ref>` and `docker compose -p ... --project-directory ... -f ... up -d --no-deps --pull never <svc>`. With real paths that is over the per-line cut (140) and can pass the body limit (360), and a command cut with an ellipsis is not the exact command. So those lines are pinned: never cut, and the other lines give way to them. For a message with pinned lines the body limit is 720 (plan v3.8 item 6, a change to the v3.7 size rule); the title limit is unchanged. A test pins the worst case (80-rune reference, 40-rune project, 60 and 70-rune paths) under 720. If a rollback is longer than that it is still kept whole. When there was no local copy of the old image, the message says "no rollback" instead of printing a command that cannot work.
8. **Weight of the upgrade message: important.** It changes what is running and what every stack sharing the tag will see, and it carries the rollback, so it uses the reserve of the rate limit.
9. **`whalenurse.actions=restart` plus `heal.pull=true`**: first built as `restart, pull`; **changed by the maintainer's decision** (follow-up 1): rung 3 requires rung 2.
10. **The loop is synchronous.** A pull blocks the loop for as long as it takes (bounded at 10 min; a recreate is bounded at 5 min and always was), and a changed pull is a pull, an `up` and possibly a forced recreate in a row. Two consequences, both handled (found in review, not by a test run): (a) `/healthz` and with it the uptime ping used to say "main loop silent" after `3*POLL_INTERVAL + 2 min` (5 min by default); `Healthy()` now tolerates an action in flight for 11 minutes **from the start of the current phase** (the pull, the up, a forced recreate each re-stamp it), so a 20-minute sequence is not one silence. (b) **`last_seen` would have gone stale**: the shutdown window of a daemon restart within one boot ends 5 minutes after `last_seen` (plan §3.3 rule 4), so a daemon restart in the middle of a pull longer than that would have put the containers it stopped outside the window, and a `restart: "no"` app that exits 1 on SIGTERM would have been started by whalenurse: the bug v3.5 fixed. While an action runs, a goroutine of its own now writes `last_seen` every 5 s (it does not touch the loop's `lastBeat`; the store's `SetMeta` is `database/sql`, safe from another goroutine). A unit test shows `last_seen` following the clock while a pull is blocked. This also covers rung 2's 5-minute recreate, which sat on that edge already.
11. **Private registries are unsupported** (plan v3.8 item 8): the compose child has no `DOCKER_CONFIG` and the image has no credentials. A login-protected registry makes the pull fail as an ordinary failed action ("pull failed", with compose's error). Documenting it is all M4 does.
12. **Compose's `pull` of a service with `build:` and `image:`** is not special-cased: a pull failure ends as an ordinary failed action, and a pull that finds the registry copy changed is followed by the `up --no-build`.

## Review follow-ups (v3.8 approved 19 Oct 2026)

The maintainer's answers to the four open questions of the first M4 build, implemented in follow-up commits on PR #12 (plan v3.8 items 11 to 15; the 720-rune upgrade message and "private registries unsupported" were approved too):

1. **Rung 3 requires rung 2.** `heal.pull=true` without `recreate` in `whalenurse.actions`: `config.ParseLabels` adds no pull rung and returns one warning ("needs recreate in whalenurse.actions"); the daemon logs a label warning once per container, so there is one warning however long it runs. Tests: the label table (default, restart only, recreate only, reordered, pull false), a daemon test that logs the warning exactly once and runs restart only, an integration test (restart only, compose never runs).
2. **Rung 2 lets an image-only drift through for `heal.pull=true` containers; config drift still blocks.** The same guard mode as before the pull (`AllowImageMove`). To notify it I added `docker.Container.ImageID` (inspect `.Image`) and an `Upgraded` event: after a successful rung-2 recreate of such a container, if the new container's image ID differs from the old one's, `Upgraded` is emitted with the old and new IDs and the rollback (tag the old image ID, then up). It is rendered as the same "upgraded during heal" message as `TagMoved`, with a line saying that someone else moved the tag. The old image ID for the rollback is the old container's `.Image`, which is what `docker image tag` takes; the integration test runs the rollback as pasted on both stores. Without the label a moved tag still blocks (the shared-tag test keeps proving it).
3. **The dependents step may take a tag that its parent's own pull moved in this incident, and only that** (`dependentMayTakeMove`). All of these must hold: the reference still resolves to what that pull produced; the pull was made by a service the sidecar's `depends_on` names (the parent's ID is gone, so the label is how it is found); the move is not older than the parent's open incident, and the incident is open; the sidecar's `com.docker.compose.image` is the image the pull replaced. Unit tests turn each condition off in turn. **The sidecar's rollback is in the same upgrade message**: when the pull starts, the sidecars of the container that run the same image reference and were created from the image about to be replaced are collected (found through the network reference or, for one that is already stale, through `depends_on`), and the rollback `up` line names the parent and them (`up -d --no-deps --pull never app side`), so one paste puts them all back. The sidecar's own recreate says nothing of its own. I chose one `up` line instead of one line per service: the tag line is the same, and the message stays shorter.
4. **`pull_policy: never` and `build` are respected.** Before the guard, `compose config --format json --no-env-resolution <svc>` is read through a new typed method (`Reader.PullPolicy`), keeping only `services.<svc>.pull_policy` (the rest of the output can hold interpolated secrets: it is dropped, not logged, and a parse error never quotes it). For `never`/`build`, or an unreadable policy (fail closed), the rung does not run: `engine.RungNotApplicable` records `RungUnavailable` (`not_applicable`), spends no rate slot, and, the pull being the last rung, SUSPENDS with the cause "pull rung does not apply (pull_policy never)". That cause is carried by the one giving-up message; I did not add a separate notification for it. A dry run reads the policy too. `--policy always` now only replaces `missing`, `if_not_present`, the refresh windows and no policy. Tests: unit (never, build, every other policy, unreadable, dry run, the command line, the parser) and integration with real compose: a `pull_policy: never` service is not pulled, and a `pull_policy: missing` service on a non-latest tag (skipped by a bare `pull` in v5.2.0 and v5.6.0) is upgraded, on all legs.

The integration test of the guard grew to match: `config --format json --no-env-resolution <one service>` is accepted from compose, and the rollback runner accepts several services (a strict name pattern).
